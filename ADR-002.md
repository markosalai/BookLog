# ADR-002: Sigurnosne mjere web aplikacije BookLog

- **Status:** Prihvaćeno

---

## Kontekst

U sklopu Koraka 5 razvoja aplikacije BookLog potrebno je implementirati sigurnosne mjere zaštite od najčešćih web ranjivosti. Aplikacija koristi Django backend s REST API-jem, JWT autentikacijom i HTML/JavaScript frontend koji komunicira s API-jem putem Fetch-a. Podaci koje korisnici unose (naslovi knjiga, recenzije, ocjene) potencijalno su izvor sigurnosnih rizika ako se ne obrade ispravno.

---

## Odluke i implementirane mjere

### 1. Zaštita od SQL Injection — Prepared Statements

**Odluka:** Korištenje Django ORM-a za sve upite prema bazi podataka.

**Obrazloženje:**  
Django ORM automatski koristi prepared statements (parametrizirane upite) za svaku interakciju s bazom podataka. Vrijednosti koje dolaze od korisnika nikada se ne interpoliraju direktno u SQL string — ORM ih uvijek prosljeđuje kao odvojene parametre driveru baze podataka.

**Primjer:**
```python
# Siguran upit - ORM automatski parametrizira vrijednosti
Knjiga.objects.filter(korisnik_id=user_id)
Recenzija.objects.get(id=id, korisnik=request.user)

# Ekvivalentni raw SQL koji ORM generira:
# SELECT * FROM knjiga WHERE korisnik_id = %s  →  [user_id]
```

Direktni raw SQL upiti nisu korišteni nigdje u aplikaciji, čime je rizik od SQL Injection sveden na nulu.

### 2. Zaštita od XSS (Cross-Site Scripting)

**Odluka:** Escapiranje korisničkog sadržaja u JavaScript template literalima pomoću `escapeHtml()` funkcije.

**Obrazloženje:**  
Frontend aplikacija dinamički renderira podatke iz API-ja korištenjem JavaScript template literala (`innerHTML`). Za razliku od Django template enginea koji automatski escapira varijable, `innerHTML` u JavaScriptu izvršava HTML sadržaj kakav jest. Bez escapiranja, zlonamjeran korisnik mogao bi unijeti `<script>alert('xss')</script>` kao naslov knjige ili tekst recenzije i taj kod bi se izvršio u pregledniku svakog korisnika koji vidi taj sadržaj.

**Implementacija:**
```javascript
function escapeHtml(str) {
    if (!str) return '';
    const div = document.createElement('div');
    div.appendChild(document.createTextNode(String(str)));
    return div.innerHTML;
}
```

Funkcija koristi `createTextNode` koji tretira sadržaj kao čisti tekst, a ne HTML. Primjenjuje se na sav korisnički sadržaj koji se renderira u DOM-u:
- Naslovi knjiga, autori, žanrovi, opisi
- Tekst recenzija i korisnička imena

### 3. CSRF zaštita

**Odluka:** Korištenje Django-ovog CSRF mehanizma s prilagođenim čitanjem tokena iz kolačića u JavaScriptu.

**Obrazloženje:**  
CSRF (Cross-Site Request Forgery) napad omogućuje zlonamjernoj stranici slanje zahtjeva u ime prijavljenog korisnika. Django ima ugrađenu CSRF zaštitu, ali budući da aplikacija koristi Fetch API umjesto klasičnih HTML formi, token se mora ručno čitati iz kolačića i slati u zaglavlju `X-CSRFToken`.

**Implementacija:**

Django postavlja `csrftoken` kolačić koji JavaScript može čitati jer je `CSRF_COOKIE_HTTPONLY = False`:

```javascript
function getCsrfToken() {
    return document.cookie.split(';')
        .find(c => c.trim().startsWith('csrftoken='))
        ?.split('=')[1] ?? '';
}
```

Token se šalje uz svaki POST, PUT i DELETE zahtjev:
```javascript
headers: {
    'Content-Type': 'application/json',
    'Authorization': `Bearer ${token}`,
    'X-CSRFToken': getCsrfToken()
}
```

Dekorator `@ensure_csrf_cookie` na web view-ovima garantira da je kolačić uvijek postavljen pri učitavanju stranice. Dekorator `@csrf_exempt` zadržan je samo na `/api/auth/login/` i `/api/auth/register/` jer korisnik u tom trenutku još nema aktivnu sesiju iz koje bi dobio CSRF token.

### 4. Validacija ulaznih podataka

**Odluka:** Serverska validacija svih kritičnih polja u `books/validators.py`.

**Obrazloženje:**  
Frontend validacija (npr. HTML `required` atribut ili JavaScript provjere) može se zaobići direktnim slanjem zahtjeva prema API-ju (npr. putem curl-a ili Postmana). Stoga je serverska validacija jedina pouzdana zaštita.

**Implementirane validacije:**

| Polje | Pravilo | Greška |
|---|---|---|
| `isbn` | 10 ili 13 znakova, samo znamenke | `ISBN mora imati 10 ili 13 znakova` |
| `godina_izdanja` | Integer između 1000 i 2026 | `Godina izdanja mora biti između 1000 i 2026` |
| `ocjena` | Integer između 1 i 5 | `Ocjena mora biti između 1 i 5` |
| `naslov` | Neprazan string | `Naslov je obavezan` |
| `autor` | Neprazan string | `Autor je obavezan` |

Validacijske greške vraćaju se kao JSON s HTTP statusom 400, s mapom polje → poruka greške kako bi frontend mogao prikazati grešku uz odgovarajuće polje.

Dodatno, `CHECK` ograničenje za ocjenu (1-5) postoji i na razini baze podataka kao dodatni sloj zaštite.

### 5. Provjera vlasništva resursa

**Odluka:** Svaki zahtjev za izmjenu ili brisanje resursa provjerava pripada li resurs prijavljenom korisniku.

**Obrazloženje:**  
JWT token identificira korisnika, ali bez provjere vlasništva korisnik bi mogao slati zahtjeve za brisanje tuđih knjiga ili recenzija jednostavnim pogađanjem ID-a resursa (IDOR — Insecure Direct Object Reference).

**Implementacija:**
```python
# Korisnik može mijenjati samo svoje knjige
knjiga = Knjiga.objects.get(id=id, korisnik=request.user)

# Korisnik može brisati samo svoje recenzije
recenzija = Recenzija.objects.get(id=id, korisnik=request.user)
```

Ako traženi resurs ne postoji ili ne pripada korisniku, Django vraća `DoesNotExist` iznimku koja se hvata i vraća kao HTTP 404.

### 6. JWT autentikacija i zaštita ruta

**Odluka:** Prilagođeni `jwt_required` dekorator za zaštitu POST, PUT i DELETE endpointa.

**Obrazloženje:**  
Umjesto korištenja DRF-ovog `IsAuthenticated` permission klase, implementiran je vlastiti dekorator koji čita i validira JWT token iz `Authorization: Bearer <token>` zaglavlja. Ovo omogućuje finiju kontrolu nad pogreškama i jasnije JSON odgovore.

```python
def jwt_required(view_func):
    def wrapper(request, *args, **kwargs):
        auth_header = request.headers.get('Authorization')
        if not auth_header or not auth_header.startswith('Bearer '):
            return JsonResponse({'error': 'Token nije pronađen'}, status=401)
        ...
```

GET endpointi ostaju javni jer pregledavanje knjiga i recenzija ne zahtijeva prijavu.

Admin rute dodatno provjeravaju `uloga == 'admin'` i vraćaju HTTP 403 za korisnike bez adminskih ovlasti.

## Razmatrane alternative

| Mjera | Alternativa | Razlog odbijanja |
|---|---|---|
| Django ORM | Raw SQL s `%s` parametrima | ORM pruža isti nivo zaštite uz čitljiviji kod |
| Vlastiti `escapeHtml` | DOMPurify biblioteka | Prekompliciran za opseg projekta; vlastita funkcija dostatna |
| CSRF kolačić | Double Submit Cookie | Django-ov ugrađeni mehanizam je pouzdaniji i bolje dokumentiran |
| Serverska validacija | Samo frontend validacija | Frontend validacija se trivijalno zaobilazi |

---

## Posljedice

- Svi SQL upiti zaštićeni su od injekcija kroz ORM
- Korisnički sadržaj u DOM-u ne može izvršiti zlonamjerni JavaScript
- Cross-site zahtjevi blokirani su CSRF mehanizmom
- Nevalidni podaci odbijaju se na serverskoj razini s jasnim porukama greške
- Korisnici mogu modificirati isključivo vlastite resurse
- Nezaštićeni endpointi vraćaju HTTP 401 ili 403 s JSON porukom greške
